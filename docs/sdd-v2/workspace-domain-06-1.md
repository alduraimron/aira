# Stage 06-1: pure Workspace domain

Status: pure representation and comparison only. [WorkspaceProvider master contract](workspace-contract.md) and [ADR-014](adr/014-workspace-provider.md) remain normative. These schemas do **not** inspect a project, authenticate a provider, retain snapshot bytes, establish store authority, prove a stable observation interval, or run a worker.

## Versions and legacy treatment

New contracts are `aira.dev/workspace-handle/v2`, `workspace-fingerprint/v2`, `workspace-fingerprint-subject/v2`, `workspace-path-manifest/v1`, `workspace-source-observation/v1` (with a separate semantic subject), `workspace-provider/v1`, `workspace-provider-capabilities/v1`, `workspace-capture/all-project-content/v1`, and a pure `workspace-lifecycle-authority/v1` reference. The latter is a key/scope placeholder, not a registered lifecycle record. The existing `workspace-handle/v1`, `workspace-fingerprint/v1` and `workspace-observation/v1` schemas, storage dispatch and attempt/context/evidence references remain unchanged, historical pre-release contracts. No v1 fingerprint contains the information needed to manufacture a v2 path manifest, source base, incarnation, or control/execution root. The current SpecStore does **not** dispatch or durably publish new workspace v2 records; later slices must version the dependent schemas and dispatch explicitly. Unknown versions/fields fail strict validation; there is no implicit upgrade, persisted v2 provider runtime or legacy v1 run mutation.

## Identities, provider and topology

The existing branded `WorkspaceId` is reused. New distinct validated brands: `ControlProjectId` (`control_project_`), provider-neutral `ProjectIdentity` (`project_`), `RepositoryIdentity` (`repository_`), `WorkspaceProviderId` (`provider_`), `SourceObservationId` (`source_observation_` + 64 hex SHA-256), `WorkspaceFingerprintId` (`workspace_fingerprint_` + 64 hex), `WorkspaceClaimId` (`workspace_claim_`), semantic `WorkspaceProviderVersion` (pinned semver), and canonical decimal-u64 `WorkspaceIncarnation` and `WorkspaceFenceEpoch`. Existing `OperationId`, `RunIdV2`, `TaskId`, `AttemptId`, run `ClaimId` and run fence remain distinct. IDs are not minted from paths; store allocation and never-recycle enforcement are deferred. An incarnation numbers a new registered resource binding; edits change the fingerprint, not the incarnation. Re-creation/relocation requires a new incarnation. Canonical u64 parsing prevents overflow; the future registry must enforce monotonicity.

`WorkspaceProviderDescriptor` pins ID, version, implementation integrity/configuration hashes and exact source, capabilities, fingerprint and preparation interfaces/policy. `WorkspaceProviderCapabilities` is a strict v1 declaration binding that descriptor; it names project kinds/topologies/dirty modes/compatible policy hashes and exact immutable base, exact overlay reproduction, deterministic fingerprint, retention, disposal, recoverable abandoned lifecycle, exclusive claim integration and repository-native *topology* separation guarantees. No filesystem/process/network/environment sandbox or termination capability exists here. Parsing alone cannot authenticate a provider declaration.

Topologies: `in-place`, `isolated-local`, `copied-snapshot`. Typed control/execution operational roots (absolute local path or opaque provider locator) are distinct roles, even in-place. Their declared same/separate relationship, literal equality, local lexical nesting and copied-snapshot base are checked without `realpath`, filesystem existence or access grants. Physical alias checking remains 06-2/06-4 work.

## Source/base and dirty decision

An observation ID is SHA-256 over its version-tagged canonical subject, **not** audit time/branch display. It binds control/project identity, registered root association digest, provider descriptor, exact inspection-policy hash, source kind and complete overlay descriptor, dirtiness and consistency. Git commits include repository identity, Git object format and full commit ID. Git observation distinguishes attached/detached/unborn HEAD, linked/main worktree association, repository-state classification and reject-v1 submodule policy with bounded observations. Branch display is diagnostic, not a commit or identity. An unborn Git HEAD can be represented as `unmaterialized` for read-only observation but cannot pass prepare validation. Bare, sparse, partial, unmerged, nested and submodule cases likewise fail initial prepare decisions.

Non-Git inspection can describe an exact unmaterialized tree digest without calling it a base. Preparation requires a declared retained snapshot with exact manifest/bytes digests, byte count, retained reference and a captured tree digest matching the reviewed tree. For a clean source the captured base tree digest must equal the reviewed tree digest. For an observed overlay they remain separate references, and 06-2 must prove that base plus overlay reproduces the reviewed tree without silently including the overlay twice. In either case this assertion still requires external proof that retained bytes exist and match. The overlay is explicitly `none` or a manifest hash plus separate staged, tracked, untracked and ignored digests and exclusions. Clean and dirty declarations cannot contradict their overlay shape. `require-clean` rejects any observed overlay; `base-only` explicitly records the reviewed overlay hash as omitted, and cannot discard dirty in-place state; `include-observed-overlay` records the included exact hash and requires provider support. Unknown/unstable observations or unmaterialized bases are not preparation authority. Source observation comparison separates repository/registration, base, overlay, dirty policy, source/provider policy and consistency changes.

## Handle, fingerprint and applicability

A v2 handle binds one `(ControlProjectId, WorkspaceId, WorkspaceIncarnation)` to registered project/repository, exact provider/capabilities, topology, role-specific roots, *complete* source observation and dirty decision, fingerprint policy, lifecycle key/fence scope, creation OperationId/actor/time and compatibility versions. It contains **no current claim assertion**. Pure claim/fence reference and claim-status vocabulary do not acquire, release or recover authority.

The v2 capture policy includes staged index stage-0 separately from tracked worktree, covered untracked/ignored content, link-target hash/size (never followed content), executable bit, tombstones and empty directories. The path manifest has one canonical exact logical project-relative path per entry; staged and worktree states for one path live in **one** entry. Git tracked paths require an explicit index stage-0 state; snapshot paths cannot claim a Git index. Nested-repository/gitlink entries are representable for later policy evolution but rejected by the initial reject-v1 capture policy. Git index/tree observation hashes are structured repository components, not raw `.git` file bytes. File content/hash/component claims are only validated structurally here; 06-2 must measure them. The manifest hash is SHA-256 of its versioned canonical sorted entries; the fingerprint digest is SHA-256 of its versioned subject including manifest and bindings, and the ID embeds its digest. Self IDs, hashes and component hashes are checked when parsing. Audit time is outside both hash subjects. The fingerprint is not a snapshot and contains no restorable bytes.

Default coverage excludes top-level `.aira` and `.git` trees, including `.aira/state/**` and authoring/materialization surfaces, **in both roles**. No broad `.gitignore` exemption exists. Explicit configuration-bound additional provider-cache exclusions must declare path, reason and affected consumers, are sorted/pinned by policy hash and cannot replace either mandatory exclusion. Excluded inputs required by a verifier need independent exact pins and boundary enforcement. A control directory visible to a worker does not become authoritative. Policy changes affect identity; future semantic changes require a new contract/policy version.

Exact validated v2 subject plus ID/digest equality is required for `identical`. Comparison reports structured `changed`, `incompatible-policy`, `different-workspace`, `different-incarnation`, `different-base` or `invalid-input` with categorical reasons (staged/tracked/untracked/ignored, mode, symlink, deletion, Git repository components, source, provider). An exact-only fingerprint applicability helper does **not** establish verifier stability, attempt authority or success. No heuristic/cross-policy equivalence exists.

## Validation boundaries and limits

All v2 objects use strict Zod objects, stable structured error codes, validated construction, detached parsed data and recursive freeze. Constructor normalization orders unordered capability lists, repository/submodule observations, overlay exclusion lists, policy exclusions and affected consumers, manifest entries and Git repository components. Persisted records must already have canonical order; duplicate or known case/Unicode-ambiguous path aliases fail rather than silently normalize. Manifest paths reuse the existing `exactPathSchema`; absolute, traversal, empty segments, globs and `.git`/`.aira` control-state entries fail. Pure path equality/Unicode checks are not provider-grade filesystem alias detection. Bounds: 250,000 manifest entries, 4,096-character logical/operational paths, 10,000 submodule observations (read-only representation), 1,024 overlay exclusions, 32 fingerprint policy pins or explicit additional exclusion declarations, 16 affected consumers per exclusion. External scan, byte and read-stability bounds belong to 06-2.

No filesystem traversal, Git commands, hash capture from disk, WorkspaceStore, claim transitions, provider preparation/disposal, Context resolver, Capability runtime, Verification runner, Scheduler, worker or Pi integration is implemented.
