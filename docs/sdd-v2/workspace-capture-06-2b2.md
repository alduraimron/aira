# Stage 06-2B2: Git/local byte closure and WorkspaceFingerprint v2

Status: read-only source capture and fingerprint composition. This layer is not WorkspaceStore, registration, preparation, restorable snapshot publication, an atomic filesystem snapshot or verifier-stable evidence. The [master workspace contract](workspace-contract.md), [06-1 domain](workspace-domain-06-1.md), [06-2A local scan](workspace-local-inspection-06-2a.md), [06-2B1 Git inspection](workspace-git-inspection-06-2b1.md) and [ADR-014](adr/014-workspace-provider.md) remain normative.

## Why composition is necessary

Git observation knows the exact base commit and object format, stage-0 index mode/OID, staged changes, tracked dirty classifications and untracked/ignored path sets. It does not know exact current worktree bytes or empty directories. Local observation hashes regular-file bytes, raw symlink target bytes, executable state and policy-visible empty directories; it cannot tell whether a path is Git tracked, untracked or ignored. `src/workspace-capture/` checks a one-to-one classification/byte closure, then uses the **existing** `createWorkspaceFingerprint` v2 constructor. It does not implement a second file reader/hash loop or a new fingerprint schema.

A two-step bootstrap is unavoidable: a `WorkspaceHandleV2` requires a stable, complete reviewed source, but 06-2A's original handle-bound scanner cannot construct that first source from a provisional Git-only projection. `inspectWorkspaceLocalTree` uses **the same** 06-2A root validation and walker with explicit control/execution roles and a validated capture policy, without a handle or a false source callback. It produces only a local tree, root audit and operational freshness ticket. `captureGitWorkspaceSource` builds a byte-complete reviewed source first. A trusted external registrar may then issue a handle binding **that exact source**; `captureGitWorkspaceFingerprint` validates this handle and re-observes the execution root. Neither operation mints a WorkspaceId, claims a resource or persists anything. The historical handle-bound 06-2A API retains its source callback requirements unchanged.

## Narrow, explicitly tagged schema corrections

06-1's path-manifest v1 index state had only Aira byte hashes; turning a 40/64-character Git OID into an Aira SHA-256 would be false. Git also has no classification for a physically empty directory. New observations use `aira.dev/workspace-path-manifest/v2`, with stage-0 `aira.dev/workspace-git-index-state/v1` `{object_format, oid, mode}` and `worktree.category: local-only` **only** for empty directories. It also permits a staged index-deletion marker beside a newly untracked/ignored file of the same path, and a physically empty parent beside an absent tracked child tombstone. The existing `WorkspaceFingerprintV2` constructor accepts this explicitly selected version and still accepts and reproduces historical v1 manifest bytes unchanged. The fingerprint ID remains the existing domain-generated Aira SHA-256 digest, not an adapter-generated ID. A Git OID is validated within its own SHA-1/SHA-256 Git domain and is never given an Aira `sha256:` prefix.

06-1's source-observation v1 subject lacked a place for even a **clean** worktree byte hash. Its Git source variant now has an optional **version-tagged** `aira.dev/workspace-git-byte-closure/v1` extension. Older v1 sources remain unchanged and parse as before; this layer refuses to treat an older/provisional source without the extension as complete. The extension binds exact Git observation hash, local-tree hash, manifest-v2 hash, Git/local/capture policy hashes and explicit byte-complete status. The source inspection policy hash is a new `aira.dev/workspace-git-source-policy/v2` subject. Thus a clean worktree byte change, Git index change, dirty byte change or policy change alters `SourceObservationId`. An observation's source ID is no substitute for the handle's separately registered authority.

## Path closure and overlay

For each stage-0 indexed path, Git OID/mode produces a tagged index state. The local path must exist with the matching Git-visible type and executable mode unless Git explicitly reports tracked deletion. A staged change's *after* mode/OID must equal the stage-0 index; staged deletion requires its absence and creates an index tombstone. A path can have stage B and worktree C simultaneously: stage B retains the exact Git OID, worktree C retains the local Aira SHA-256 or raw link-target descriptor. Git-reported tracked deletion produces an explicit worktree tombstone without requiring a nonexistent local entry. A staged deletion followed by recreation has index tombstone plus Git-classified untracked/ignored local bytes. Heuristic renames remain old-path deletion plus new-path addition. Symlinks are never followed. Non-executable permission bits are not fingerprint identity.

Every ordinary local regular/symlink must be explained by the index, Git untracked set or Git ignored set; an unknown local file fails. Every Git path expected to exist must be present locally; missing paths fail unless Git explicitly declares deletion. Local empty directories are `local-only`, not fabricated Git untracked files. They affect the manifest and are dirty local overlay for `require-clean`, even if Git itself reports clean. A physically empty directory can coexist with an absent tracked tombstone beneath it. Git-only index and local-only paths cannot alias under the 06-2A/06-2B1 grammar. Both top-level `.aira/**` and `.git/**` remain excluded; Git's separate audit may still report tracked `.aira` paths. Declared cache exclusions are applied identically by both policies; no `.gitignore` omission is inferred. Gitlinks, submodules, nested repositories, sparse/partial states, unborn/bare HEAD, conflicts and unsafe index flags never yield a complete fingerprint.

The source overlay keeps separate canonical hashes for staged Git changes, tracked worktree changes **with exact local states**, untracked local states, ignored local states, local-only empty directories and declared exclusions. The overlay digest does not include the physical worktree locator: equivalent included overlays can be compared across linked worktrees of the same repository and base. The source byte-closure extension separately binds each worktree's Git observation hash and exact local manifest. Base commit and overlay remain distinct. This is identity/inventory, not a promise that 06-4 can reproduce it or that Git objects are retained.

## Coordinated capture and freshness

The effectful API validates supplied intent, obtains G1 from the existing read-only Git adapter, obtains L from the existing 06-2A walker, obtains G2, compares canonical Git semantics and policy/operational root associations, then performs a **post-G2 local stat recheck** through 06-2A before pure composition. That final recheck covers captured files, links and directories and detects an already-dirty file whose bytes changed after L while Git still reports the same `M`. It reads metadata only, never rehashes file bytes. The pure API validates the versioned Git/local observations and performs path closure without filesystem or process calls. Tests demonstrate that Git HEAD/index/classification drift, root substitution, post-local byte edits and local scan mutations do not mint a fingerprint.

G1/L/G2 agreement plus metadata rechecks is still **best-effort race detection**. A transient write-and-revert, metadata restoration, hostile same-UID ancestor swaps, writes after the last check or changes during verifier consumption remain unproved. An optional caller-supplied `aira.dev/workspace-capture-quiescence/v1` token must be affirmed unchanged at both ends before the source is marked `consistency: stable` and a fingerprint is returned. Without it the byte-closed source has `consistency: unknown`, and capture is incomplete. This assertion is trusted host input, **not** an authenticated lock, WorkspaceStore claim, scheduler fence or standalone security guarantee. A lying callback does not create authority. Real lifecycle ownership and verification-grade input stability require later 06-3/06-5 and runner/backend coordination.

For in-place roots, the exact reviewed handle source must match the freshly completed execution source, including its ID and semantic subject. For separate roots, the handle's reviewed control source remains distinct from the execution source; the host must freshly re-observe that registered source before and after execution capture through an explicit trusted callback. `base-only` with dirty reviewed control is allowed only when the separate execution tree itself is clean. `include-observed-overlay` additionally requires byte-identical path-manifest/overlay identity across roots. `require-clean` rejects all covered Git and local-only dirty categories. A dirty in-place `base-only` handle remains invalid under 06-1 and cannot be laundered into a clean execution fingerprint. No source is silently refreshed or replaced in a handle.

The pure capture result carries G1/G2, local observation, a structured closure report (tracked/staged/tracked-dirty/untracked/ignored/deletion/local-only counts, exclusions, unsupported paths, mismatches), the completed execution source where available, the exact existing v2 fingerprint only on complete closure, and stable diagnostic codes. `compareWorkspaceFingerprints` and `workspaceFingerprintApplicable` retain their existing exact-only evidence semantics. Audit times, scan order, index file stat/cache bytes and OS inode diagnostics do not enter the local content hash or fingerprint digest; the provisional Git repository/worktree association remains a **local physical association**, not a portable repository UUID. File atime may change from reads.

There is no WorkspaceStore, lifecycle transition, claim, fence, checkout, reset, stash, worktree creation, retained snapshot, persisted capture, Context resolver, worker, CLI, verifier success judgment or Git commit in this slice.
