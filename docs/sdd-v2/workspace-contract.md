# Aira SDD v2 WorkspaceProvider master contract

Status: accepted target architecture for Stage 06. Normative under [ADR-014](adr/014-workspace-provider.md), [ADR-010](adr/010-workspace-and-execution-backends.md), and the [stable invariants](invariants.md#context-capabilities-and-workspaces-adr-006-adr-010-adr-014). This document specifies the whole target, not currently implemented behavior. 06-MASTER changes contracts only. `MUST`, `MUST NOT`, and `REQUIRED` are normative.

WorkspaceProvider answers: **what exact project state will an attempt operate on, where may it operate, who owns that mutable workspace, and what exact state was observed for verification?** It does not grant file permissions, choose context or tasks, execute/sandbox workers, or judge verifier success.

```text
trusted control project/root (.aira/state/v2, Steering, Specs, runs)
                 | exact source observation and lifecycle authority
                 v
       WorkspaceProvider + WorkspaceStore
                 | immutable handle, base/overlay, fingerprint, fenced claim
                 v
     execution root (worker-visible mutable project tree)
                 |
      later Context / Capability / ExecutionBackend / Verification
```

The **control root** is the trusted host's Aira authority and source-project reference. The **execution root** is the attempt's project tree. These are distinct *roles* even for an explicitly selected in-place provider with equal physical roots. Never pass an undifferentiated `projectRoot` between boundaries. The host retains control-root authority; future worker launch normally receives only an execution-root reference. An in-place topology cannot meet that access separation merely by naming two roles.

## Identity and version discipline

Use strict, branded, validated identities following [domain conventions](domain-contract.md#version-and-identity-conventions): opaque lower-case `<prefix>_<token>` for new logical IDs (`project_`, `repository_`, `workspace_`, `source_observation_`, `workspace_claim_` if a dedicated claim namespace is needed); `OperationId`, `RunIdV2`, `TaskId`, `AttemptId`, `ClaimId`, and `ContentHash` retain their existing distinct types. `WorkspaceIncarnation` and `WorkspaceFenceEpoch` are *separate* branded canonical decimal u64 strings, checked for overflow. No raw `string` alias stands for all identities. A future schema/record inventory MUST give new persisted contracts literal `aira.dev/<contract>/vN` discriminants and fail unknown versions closed; semantic changes to an existing fingerprint or preparation policy require new version/policy identity. Use existing canonical JSON v1 plus SHA-256 for Aira semantic digests; Git object IDs retain their explicitly named Git object format.

| Identity | Scope and purpose | Not interchangeable with |
| --- | --- | --- |
| `ControlProjectId` | Minted, durable identity of one registered Aira control project; shared by its Specs/Steering/workspaces | Absolute path, Git root, `SpecId` |
| `ProjectIdentity` / optional `RepositoryIdentity` | Provider-neutral registered source-project identity; repository identity further identifies a verified repository association when available | Git branch, Git commit, path |
| `WorkspaceId` | Never-recycled logical workspace object, scoped to `ControlProjectId` | Path, mutable content digest |
| `WorkspaceIncarnation` | Monotone per-WorkspaceId resource-binding generation; changes on re-creation/rebinding of execution resource, not on edits | Fingerprint, ownership epoch |
| `WorkspaceHandle` | Immutable description of precisely one `(ControlProjectId, WorkspaceId, WorkspaceIncarnation)` | Current lifecycle state |
| `SourceObservationId` | Exact reviewed source observation: base plus overlay inventory/hash and inspection policy | Branch name, audit timestamp |
| `BaseRevision` | Typed Git commit or retained content-addressed snapshot of immutable starting material | Included mutable overlay |
| `WorkspaceFingerprint` | Versioned identity of *observed mutable contents* at a point; repeats for equal semantic state in the same incarnation | Restorable snapshot, fence |
| `WorkspaceClaimId` / `WorkspaceFenceEpoch` | One exclusive ownership event and monotonically advanced authority epoch for that WorkspaceId | Run task claim/fence, PID |

A new workspace or incarnation is minted only by authoritative registry publication, never inferred from directory naming or a moved path. Reuse of `WorkspaceId` for a different project is forbidden, even after disposal. Changing registered source association requires explicit reconciliation/new project registration, not matching by path. Non-Git projects need at least a durable minted project identity bound to an observed source-tree digest and registered root association; a provisional read-only inspection without registration is not preparation authority. Where no external durable repository identity exists, Aira can establish *its own* project continuity but cannot prove that a copied tree on another machine is the same project. A Git clone with the same HEAD is not proof of identical registered repository identity either.

## Ports, observation, and handle

The pure provider-neutral contract owns identities, requests, handles, fingerprints, capabilities, comparisons, lifecycle transitions and structured errors. Effectful adapters implement inspection/preparation/capture/cleanup; WorkspaceStore owns durable lifecycle authority. `WorkspaceProvider` needs at least these conceptual operations (names are illustrative, semantic inputs/outputs are not):

- `inspectProject(controlRoot, policy)` returns a registered or provisional project identity, source topology/repository observation, supported/unsupported conditions, and an exact `SourceObservation`. No mutation or ownership implied.
- `prepare(request)` validates expected registered project, exact reviewed observation, provider/policy and OperationId; it publishes or returns an immutable handle for the created/bound incarnation and a fingerprint of the prepared state. No worker dispatch implied.
- `inspectWorkspace(handle)` checks actual provider resource identity against the registered handle, returns integrity/lifecycle diagnostics without promoting a directory to authority; `fingerprint(handle, policy)` returns an observation or an explicit unstable/unsupported result. Neither changes lifecycle.
- `acquire`, `checkOwnership`, `release`, `inspectRecovery`, `recover`, `retain`, and `dispose` operate through fenced WorkspaceStore transitions with expected registry state/operation identity. A pure inspection/fingerprint needs no OperationId; no workspace TTL renewal is implied by the initial durable-claim model.

`WorkspaceHandle` is immutable **per incarnation**, strictly versioned (target `aira.dev/workspace-handle/v2`, not reinterpretation of the existing v1 record), with at least:

- `(ControlProjectId, WorkspaceId, WorkspaceIncarnation)` and exact provider kind, implementation/version/integrity, configuration hash, preparation policy/version, compatibility interface versions;
- provider-neutral `ProjectIdentity`, optional verified `RepositoryIdentity`, and explicit topology (`same-root/in-place`, `isolated-sibling/worktree`, `copied/snapshot`, or an explicitly versioned other topology);
- typed operational control-root and execution-root references (local absolute path where local, opaque provider locator otherwise), and a declared relationship/overlap check; references are **locators**, not identities or capability grants;
- exact immutable base revision and included-overlay observation (or explicit `none`), source observation ID and dirty-state decision; creation OperationId, actor/source provenance and audit time;
- exact versioned workspace capability declaration, fingerprint policy and compatible source/provider contract versions;
- an authoritative WorkspaceStore lifecycle/claim *key and fence scope*, **not a frozen assertion that a mutable lease is still active**. Current claim/retention/disposition is read with CAS from the store. Provider data is typed/versioned or explicitly bounded JSON and never confers authority by itself.

A handle that points to a missing or substituted resource is historical metadata, not a live workspace. A moved workspace retains its logical ID **only** through an authorized registry relocation that verifies the original resource and new destination and publishes a new incarnation/handle; reusing path text cannot establish identity equivalence. Compatible readers preserve original v1 records as historical data; no decoder silently fills missing v2 fields.

### Topology and layout

Local isolated execution roots SHOULD live in a trusted host-managed sibling area *outside* `.aira/` and outside the control root, with opaque, injectively encoded project/workspace/incarnation segments; the exact base directory is configured, not a source of identity. Do not place worker-mutable execution trees inside `.aira/state/**` or expose that tree as worker scratch. Provider-owned Git metadata and registry records remain host-owned. `same-root/in-place` requires explicit opt-in and reports **no topology isolation**. A separate path/tree grants topology separation only; it is **not OS-enforced security isolation**. A container/remote backend is an ExecutionBackend matter, not a workspace security label.

## Source and preparation contract

`SourceObservation` (target `aira.dev/workspace-source-observation/v1`) pins registered control project, source/root association, provider inspection/policy/version, immutable base, complete relevant mutable source state, `SourceObservationId` derived from its canonical semantic subject, stable/unknown consistency and nonsemantic audit metadata. For a *prepared* workspace, `BaseRevision` is a discriminated union: exact Git commit (object format plus full object ID and verified repository association), or durable retained content-addressed snapshot manifest plus bytes. A read-only non-Git `SourceObservation` may instead carry `base: unmaterialized` and an exact tree observation digest; this is not a `BaseRevision` or preparation authority. The later snapshot-capture step must prove that its retained manifest and bytes match that same reviewed tree observation, bind the new snapshot base to the original source observation and fail on drift. A merely calculated tree digest is an *observation*, not a restorable snapshot. A non-Git prepare cannot claim an immutable base until its exact bytes/manifest are retained and verified. Source overlays record separately staged/index state (where meaningful), tracked working changes, untracked/ignored included content and exclusions with manifest hashes; `none` is explicit. Immutable base and overlay are never conflated. Git branch/HEAD label and timestamps can be diagnostic but not base identities.

`PrepareRequest` (target `aira.dev/workspace-prepare-request/v1`) binds `ControlProjectId`, provider/config/version and capability requirements, chosen topology, exact `BaseRevision`, reviewed `SourceObservationId` plus complete observation/policy reference, dirty policy, desired fingerprint policy, optional run/task/attempt intent and a mandatory `OperationId`. For a non-Git unmaterialized read-only observation, immutable snapshot capture is a separate explicitly bound pre-prepare phase; the request cannot be accepted as ready until it supplies the resulting verified snapshot base and proves that it came from the exact reviewed tree digest. The **expected source association and complete source observation** are preconditions, not hints. Target resource allocation and publication use registry CAS. The result binds a handle, prepared fingerprint, source decision and lifecycle record. Provider cannot silently substitute HEAD/current path, retry against a newer source, downgrade capabilities or choose a different topology. If source changes after review, default is **fail stale**. An explicit caller `re-observe` decision creates a *new* observation and prepare intent (and renewed review/authorization as needed), never silently reuses the original OperationId/provenance. The provider checks expected source freshness before any materialization and again before publishing a usable handle; it verifies the execution state against the planned base/overlay after materialization. A source edit between those checks fails even if a captured copy is internally consistent, unless an explicit new observation/intent is authorized. If exact source stability cannot be established during capture/materialization, fail/return unknown; a matching hash after two racy scans alone cannot certify an uninterrupted stable interval.

Dirty policy is a required closed choice:

| Policy | Required behavior |
| --- | --- |
| `require-clean` | No applicable overlay relative to base, including index/staged, tracked, untracked and ignored content covered by the pinned policy (excluding only declared non-project controls). Fail if dirty. |
| `base-only` | Use **only** the exact immutable base. Record reviewed source observation and explicitly discarded/not-carried overlay hash/reason; never claim that the control tree was clean. In-place with dirty source cannot implement this without modifying user files and MUST fail. |
| `include-observed-overlay` | Reproduce precisely the observed overlay on the selected base, including Git index/staged versus worktree distinctions and all covered files. Verify the prepared state against the expected manifest/fingerprint; approximate copying fails. If the provider cannot guarantee this, report unsupported. |

Policy does not license destructive cleaning of the source root. For Git `base-only`, even if dirty material is not included, review must bind its exact source observation so changed dirty state cannot silently satisfy an earlier prepare request. For in-place use, the actual current execution state must match the chosen source observation at handoff; the provider does not claim future immutability.

A `WorkspaceSnapshot` is a separately named, durable, content-addressed *restorable* manifest and bytes (or provably pinned Git object closure), with retention/availability and reproduction semantics. A `WorkspaceFingerprint` contains no bytes and cannot restore a workspace. A snapshot cannot be inferred from a fingerprint alone. Missing snapshot bytes fail reproduction; Git object availability must be checked when re-preparing.

## Fingerprint policy and exact state

`WorkspaceFingerprint` target `aira.dev/workspace-fingerprint/v2` has a strict versioned envelope: `(ControlProjectId, WorkspaceId, WorkspaceIncarnation)`, registered project/repository association, exact provider implementation/version/configuration, `BaseRevision`, exact versioned fingerprint algorithm and capture/exclusion policy (including its hash), canonical semantic state components and lowercase SHA-256 digest. Capture time, PID, inode, fs timestamps and scan order belong in a separate `WorkspaceObservation` diagnostic envelope, not in the semantic hash. `sameWorkspaceFingerprint` is exact version/policy/provider/incarnation/base/components/digest equality, never digest-only comparison or cross-policy equivalence. Durably used fingerprints also reference a retained immutable *path-identity manifest* (path/type/content-hash/index-state entries, not file contents) by its own content hash; the manifest lets an attempt explain which paths and staged/worktree states changed without falsely promising restoration. Missing or mismatched required manifest data fails later provenance use. Hashes do not provide proof against a malicious owner coherently replacing the store.

Hash subject: a version-tagged canonical JSON v1 value over those semantic bindings and a sorted list of canonical root-relative logical path entries. Entries encode type, path (no traversal/aliasing; provider rejects ambiguous case/Unicode aliases rather than normalize silently), content SHA-256 or raw symlink target hash, relevant executable/mode bits, deletion marker and Git index stage where applicable. Paths are sorted in code-point order after validated canonical encoding; arrays and maps are canonicalized explicitly. Directory entries are included for empty directories under the initial policy. Other directory mtimes are not identity. Unsupported special files, unstable reads, ambiguous aliases or unsupported Git index conflict stages fail rather than hash arbitrary bytes. Semantic equality never depends on enumeration order, inode allocation, timestamps or scheduling. SHA-256 is used for Aira content components even if the pinned Git commit uses Git SHA-1. Known SHA-1 object limitations remain; the provider must validate Git objects it relies on, not treat an asserted object ID as authenticated Aira bytes.

Default v1 target capture policy (`aira.dev/workspace-capture/all-project-content/v1`):

| Material | Treatment |
| --- | --- |
| Git tracked worktree modifications and deletions | Included as path/type/content/mode or explicit absence versus pinned base; rename is two path changes, not a heuristic status label. |
| Git index/staged state | Included **separately** by canonical stage/path/mode/blob-content identity; identical worktree bytes with different staged content differ. Git index file inode/stat cache bytes are not semantic identity. |
| Untracked files and ordinary ignored/generated files | Included by path, type, content and mode by default, even if `git status` omits them. Bounded capture must fail explicitly if infeasible. No silent cache exemption. |
| Symlinks | Include link type and exact target bytes, do not follow links for content capture. Unsafe escaping/dangling/substituted links fail where access/preparation cannot be safe; executable read resolution belongs to later stages. |
| Submodules and nested repositories | Versioned policy requires explicit handling; initial local/Git implementation rejects both rather than traversing/ignoring them. Later supported recursive mode must bind gitlink commit **and** nested mutable/index/untracked state under its own policy, or prohibit nested mutation. |
| File mode | At least file type and executable bit, plus link type/target; irrelevant permission/owner/xattr bits are excluded unless a new policy requires them. If verification depends on them, default evidence is not sufficient. |
| Empty directories | Included (even though Git does not track them); changes in membership affect digest. |
| `.git` metadata | Excluded from execution-content identity, including worktree `.git` link. Repository/base/index semantic data is represented separately; provider metadata integrity is checked independently. |
| `.aira/**` including `.aira/state/**`, Steering materializations and derived control views | Excluded **in both roots** by initial policy. Control-plane churn cannot invalidate implementation evidence; these are host-controlled inputs via exact Steering/Spec/Context pins, not workspace content. A provider MUST deny worker-mutated control data as an authoritative input. |
| Provider scratch and optional future cache exclusions | Only host-managed directories outside the execution root, or an explicit versioned exclusion policy naming paths, reasons and affected consumers. No implicit `.gitignore`-based omission. |

Excluded control inputs do not cease to matter: verifier/attempt applicability independently checks pinned Spec/Steering/context/policy. An operation requiring excluded `.aira/**`, provider metadata, xattrs or other excluded inputs must pin them independently or use a new capture policy **and** a permissible control/worker boundary; it cannot rely on default workspace evidence. Arbitrary non-hermetic verifiers that may read excluded or out-of-root inputs cannot assert full exact-workspace coverage without a separately enforceable/stable input contract. Policy incompatibility or inability to prove covered inputs fails preflight, not a passing verifier result. A fingerprint can detect content drift under its policy but is not a security or atomic filesystem snapshot.

`WorkspaceObservation` includes fingerprint, interval/diagnostic time, policy, coordination contract, and `stable`/`unstable`/`unknown` result. `stable` requires a proven capture boundary under trusted ownership/quiescence and repeatable read of the same contents; double-scan agreement alone does not rule out transient writes. For verification, runner/backend must additionally establish no uncharacterized mutation *during verifier input consumption* and recheck before applicable publication. Before/after matching fingerprints alone do not prove a stable interval (a write-and-revert is possible). If that stronger guarantee is not available, evidence is `unknown`/historical under ADR-007; WorkspaceProvider supplies observations, not a success judgment.

## Durable lifecycle, ownership and cross-domain fencing

A first-class, provider-neutral `WorkspaceStore` is REQUIRED; neither SpecStore, SteeringStore, a Git ref, a lock directory, nor the execution tree is the workspace registry. The control-root-owned store authoritatively selects registered project identity, immutable handle/incarnation history, source/provenance, current lifecycle, exclusive claim, monotone workspace fence and retained/disposed tombstones. Its own HEAD/CAS and verified immutable records use the storage contract's lock, expected state, OperationId and crash/durability principles, with a distinct authority scope and no invented Spec record. BlobStore may hold shared immutable snapshots/records. The current immutable file-store `FORMAT` and unknown-namespace guard do **not** already permit adding a `workspaces/` directory under `.aira/state/v2/`: 06-3 MUST specify a compatible explicit FORMAT/layout evolution or an independently certified registered store location, with migration and failure behavior for existing stores, before creating a WorkspaceStore namespace. Directory presence is only evidence for inspection, never registration or ownership. Orphan directories are quarantined/inspected, not adopted by their names.

The initial model is a **durable exclusive claim with explicit recovery**, not an expiring workspace TTL. This avoids auto-stealing a mutating tree based on a paused process or wall clock. Liveness/heartbeat/owner scope is diagnostic; PID alone or expired run-task lease is not workspace transfer authority. Claims bind handle/incarnation, run, task, attempt, owner implementation/instance identity, acquisition `OperationId`, `WorkspaceClaimId`, strictly increasing `WorkspaceFenceEpoch`, acquisition metadata and corresponding task claim/fence reference. At most one active/reserved exclusive claim per incarnation; check and transition under WorkspaceStore CAS. A provider MUST additionally bind a verified physical-resource reservation key in host authority so two different WorkspaceIds or control projects cannot claim an aliased execution tree concurrently. If the provider cannot prove uniqueness across its managed area and registered in-place roots, it rejects the second binding/claim; a path string or inode alone is not semantic identity or an adequate global lock. This resource reservation is separate from the logical workspace key and checked again on recovery/disposal. Each new ownership acquisition after release or recovery increments the per-WorkspaceId workspace epoch, never reuses a claim ID or fence. No counter increments for ordinary filesystem edits or reads. `WorkspaceIncarnation` changes only for a new verified physical resource binding; mutable content identity is its fingerprint. No workspace lease renewal is required in this model; any future renewable remote-provider lease must be an explicitly new compatible contract with monotone fencing and fail-closed lease loss, not an age heuristic.

The run/task claim from ADR-003 is **independent** authority with its own `FenceToken`, `RunGeneration` and lease. Effective mutating dispatch/publication requires **both** current claims for the same `(run, task, attempt, handle/incarnation)`, and an applicable approved Spec snapshot. The workspace epoch does not replace the run epoch; neither can be inferred from the other. Run expiry or Spec supersession fences run authority, even if the workspace claim is still reserved. Workspace recovery fences workspace authority, even if run bookkeeping still says active. Stale owners cannot publish release, retain, disposal or claim transfer, nor attempt/evidence success, after either fence changes.

Separate WorkspaceStore and SpecStore HEADs have **no cross-store atomic transaction**. Future Core coordination MUST serialize dual-domain dispatch/result transitions with a fixed short-lock order: workspace authority lock then affected Spec lock, inspect/check both exact HEADs and fences, commit with expected states, recheck effective dual authority. Do not hold either lock across worker execution, verification, human waits, or filesystem copy. Reservation precedes task-claim publication; no dispatch until both commits are durable and rechecked. A crash between them leaves a non-dispatchable reservation for explicit reconciliation. Run result publication must validate workspace claim/fingerprint under this coordination **while committing** through SpecStore CAS; a prior read followed by an unlocked Spec commit is insufficient. Existing uncoordinated SpecStore API use cannot assert this property; integrating the coordinator is deferred. Lock/order violations or missing coordination fail dispatch/publication closed. A Spec supersession may revoke its task claim first, leaving a workspace reservation to reconcile; it cannot grant a new workspace owner while the old owner is still eligible to publish. Recovery fences workspace authority before transferable publication, then reconciles run claims; partial dual-domain states remain non-dispatchable. Idempotent resume examines both committed histories rather than guessing from an acknowledgement.

Lifecycle status is separate from immutable handle. Target state machine:

| State | Meaning / allowed next action |
| --- | --- |
| `preparing` | Durable intent/reservation before complete resource verification; recover to `available`, `retained` or `manual-reconciliation`. |
| `available` | Verified reusable incarnation with no claim; acquire only after freshness and policy checks. |
| `claimed` | One current exclusive reserved/active attempt claim; release after safe quiescence to `available` or `retained`. |
| `abandoned` | Owner lost or run fenced, contents preserved, no new dispatch; inspect/recover. |
| `recovering` | One fenced recovery operation in progress; no dispatch. |
| `retained` | Preserved for inspection/debugging, fingerprintable read-only under host coordination; not auto-claimable. |
| `disposing` | Fenced cleanup intent; no dispatch, resumable by same OperationId. |
| `disposed` | Terminal tombstone; identity/fence history retained, resource removal verified. |
| `manual-reconciliation` | Unprovable safety, ambiguous liveness, mutated/unrecognized resource or partial cleanup; no automatic reuse/deletion. |
| `unknown` | Resource/store integrity or observation insufficient to classify; only explicit inspection/reconciliation. |

`released` is a **claim status**, not a claim that the directory disappeared. Explicit recovery distinguishes same-scope demonstrably dead owner, ambiguous process table/descendants, observed post-loss mutation, missing provider resource, unexpected fingerprint, and partial preparation/disposal. Clearly dead owner is not proof all descendants stopped. Recovery first advances the workspace fence under CAS and marks old claim abandoned/fenced, retaining last known and newly observed fingerprints and run/attempt provenance. Reuse of the *same physical tree* requires positive quiescence proof, resource/handle verification and an explicit content decision under a new claim; otherwise preserve it and prepare a **different incarnation or WorkspaceId at a different location** from known material if policy permits. In-place cannot auto-transfer while liveness or mutations remain ambiguous. An unprovable resource enters `manual-reconciliation`/`unknown`. Never auto-delete work on age, missing PID alone, or a failed test. Manual reconciliation records inspected identity, observed fingerprints, uncertain effects, actor/authorization and disposition under CAS; human authorization does not bypass resource/path verification or restore a fenced attempt. This is workspace lifecycle recovery, not an assertion that an interrupted attempt's external effects are safe to retry (ADR-009).

## Operations, idempotency, crashes and disposal

Every mutating operation (`register`, `prepare`, `acquire`, `release`, `recover`, `retain`, `dispose`, relocation) carries a caller-supplied `OperationId` and complete canonical intent with expected store HEAD, handle/incarnation, lifecycle/fence, source observation and affected run intent where relevant. Same ID + same complete intent returns the original committed result after any later transactions; same ID + different intent conflicts. Retries do not repeat unrecorded external effects or silently adopt orphan output. A new intent after changed source/fence uses a new OperationId. For multi-phase prepare/dispose/recovery, the public OperationId identifies the immutable *whole-operation intent*; each internal authority publication has its own uniquely identified phase/child operation and expected state, so one ID is never reused for two different transaction intents. Replay inspects the recorded phase chain and resumes or returns the exact completed result, rather than replaying side effects blindly. Read-only inspect/fingerprint has none. A long filesystem preparation/disposal is **not** held inside the short store lock: publish durable preparing/disposing intent with verified expected identity, perform provider side effects idempotently against a reserved collision-safe resource, verify result, then publish final state under fresh CAS; a crash at any step yields prior or new complete lifecycle authority, plus possibly quarantined/partial external files. Resume must compare on-disk exact resource identity and intent, not replay a blind copy/delete.

Release requires matching current workspace token **and** coordinated run disposition and quiescence; a stale token cannot release the new owner's claim. Retain is explicit on failed/interrupted/unknown attempts or operator request, records reason, actor, last observation, and prior claim/fence; retention does not restore attempt authority. Retained trees may be inspected/fingerprinted under safe coordination but require explicit reconciliation/new authority to be mutable. Dispose verifies registered handle/incarnation, current fence and allowed unclaimed/quiesced lifecycle, exact provider-managed resource identity, root containment and no unexpected files/links/overlap. It MUST NOT recursively delete based only on a handle-supplied path, symlink target, directory name or stale metadata. When unexpected user data, substituted ancestors, open writers, or unprovable scope exists, fail closed into retained/manual reconciliation; prefer leaking an orphan to deleting the wrong tree. A partial cleanup leaves a durable `disposing`/manual state, never a false `disposed`. A finished disposal keeps identity/fence tombstones; no later same-path directory is automatically associated with it. In-place disposal **never** deletes the control project; it only closes the Aira workspace binding after verification.

Failures are structured, deterministic diagnostics (at least unsupported schema/provider/policy, unregistered project, source stale, overlay unsupported, capture unstable, resource missing/substituted/collision, ownership busy/fenced, operation reuse, unsafe path/disposal, storage integrity, and manual reconciliation required). A transient observation is never recast as clean or as an absent workspace.

Local adapters MUST validate configured roots and each affected ancestor for traversal, symlinks, nested mounts and provider-managed scope; detect collision, hardlink/alias risks, nested workspace/control overlap, replacement and unsafe deletion targets. Restrict cleanup to a positively identified host-managed area, with identity checks immediately before each destructive step. Provider operations MUST report unprovable path race safety instead of guessing. Stronger adversarial concurrent path confinement requires kernel-level dirfd/openat-style primitives later; current Node pathname rechecks are not that guarantee.

Supported crash guarantees concern **lifecycle authority**, not rollback of worker modifications: at preparation/acquisition/release/recovery/disposal boundaries, either prior or complete committed WorkspaceStore state is authoritative; uncommitted files/operations are non-authoritative; missing ack is resolved via committed OperationId history. Fsync, atomic publication, integrity checks, exclusive locks and platform certification follow [storage-contract.md](storage-contract.md). Externally mutable workspace bytes can remain partially changed after any worker crash, even with an intact registry. No exactly-once process/file side-effect claim follows from metadata idempotency.

## Provider capability and compatibility contract

Each provider exposes an authenticated, versioned declaration (target `aira.dev/workspace-provider-capabilities/v1`) pinned with its implementation/version/integrity/config hash in the handle and source/fingerprint policies. It states *supported operations/guarantees under this configuration*, not desired labels: supported project kinds, topologies, dirty modes, immutable-base availability, exact overlay reproduction, deterministic fingerprint policies, exclusive-claim integration, crash recovery/cleanup and repository-native **topology** isolation. Preflight checks required capabilities against the concrete provider + WorkspaceStore; unsupported combinations fail, no silent fallback. Provider identity/version or policy changes that change semantics require a new version/policy and new handles/observations. Earlier handles remain interpretable under pinned semantics or fail closed if implementation is unavailable.

No provider capability asserts filesystem/process/network/environment confinement, worker termination, permission to write, or verifier success. Those belong to Capability Engine and ExecutionBackend. `in-place != sandboxed != write-confined`; an isolated worktree is not a sandbox either. Worker access to `.aira/state/**` and arbitrary file mutation is a later backend/capability enforcement concern. Stage 06 only models trusted host coordination and operational paths.

## Git and non-Git target behavior

For Git-backed inspection, verify a non-bare worktree, resolve the enclosing Git toplevel and common repository association (including `.git` file in linked worktrees), Git object format, exact HEAD **commit object** and effective index/worktree state. Attached branch and detached HEAD are both supported if HEAD resolves to a commit; branch name is nonsemantic. Base is the resolved commit, not the mutable branch ref. Reject moving HEAD, object unavailability, worktree/repository replacement, unmerged index, unsupported sparse/partial checkout, submodules or nested repositories under initial local/Git policy. Bare repos and unborn HEAD are unsupported for preparation and report explicit reasons; do not invent an empty commit. Linked worktrees have independent workspace identities and index/overlays even when their Git common-dir/repository identity agrees. Repository root is an operational association checked against project registration, never the identity by itself. Git ignored files follow the pinned default include policy; `.git` internals and `.aira/**` remain excluded, not lost through Git status output.

Read-only non-Git inspection may identify a registered local project and fingerprint its exact ordinary tree under a versioned filesystem policy. A non-Git prepare requires a retained immutable snapshot manifest/bytes for a base, plus explicit overlay decision and provider support. 06-4's first concrete provider may support only certified Git isolated worktrees; non-Git preparation, dirty-overlay reproduction and in-place are target capabilities, **not** implied initial features. Unsupported inputs fail explicitly rather than pretending the target provider handled them. Snapshot-backed/copy/remote strategies may later implement the same handles, identities, provenance and lifecycle without changing the core domain.

## Downstream boundaries and security model

- **Attempt:** future versioned attempt/run bindings carry exact handle/incarnation, starting and ending fingerprints, source/base/overlay, provider/policy, workspace claim/epoch, run claim/fence, and selected ExecutionBackend identity. Existing `aira.dev/attempt/v2` stores a single fingerprint and must not be claimed to have these new fields. If a crash prevents reliable end capture, record an explicitly unknown end observation, never fabricate an ending fingerprint. No attempt execution is implemented here.
- **Context:** later resolver consumes exact handle/fingerprint/execution root/source identity and pinned Steering/Spec inputs to select delivered files. It does not grant permission. WorkspaceProvider does not choose model context.
- **Capability/ExecutionBackend:** later policy decides allowed paths under execution root; backend/tool enforces all required read/write/process restrictions at actual I/O. WorkspaceProvider only identifies topology/root. Never claim an unrestricted local worker is confined because it has a worktree.
- **Verification:** runner consumes exact workspace and provider fingerprints, establishes stable observation/runner boundary, captures evidence against the fingerprint it actually evaluated and exact attempt/backend inputs. Evidence for A cannot prove B without a future *explicit* equivalence applicability contract. Provider cannot decide pass/fail. Current exact-workspace evaluator remains conservative.
- **Scheduler:** calculates readiness and run/task claims under ADR-003/005 and requests workspace through Core coordination; provider cannot decide DAG readiness or scheduling. No cyclic domain dependency: workspace only accepts exact intent/bindings, not scheduler code.

Trust: host Aira, control-root owner, correctly configured registered provider and certified local Linux filesystem/kernel. Worker/model output, repository files and provider-supplied locators are not authority. No Stage 06 claim of resistance to a malicious control-root owner, a malicious same-OS-permission process, arbitrary worker escape, coherent store rollback, adversarial ancestor-swap races with current Node APIs, distributed/network-filesystem consistency, or exactly-once external effects. The 05C audit's residual limitations carry forward. A stronger local security claim requires separate owner/OS permissions, kernel-resolved path handling and an enforcing backend; a distributed claim requires a certified distributed authority/fencing mechanism, neither provided by abstraction alone.
