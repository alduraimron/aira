# Stage 06-2A: read-only local workspace inspection

Status: implemented local observation adapter, **not** Git observation, a filesystem snapshot, WorkspaceStore authority, preparation, or verification-grade stability. The normative policy remains [workspace-contract.md](workspace-contract.md) and the exact pure schemas remain [workspace-domain-06-1.md](workspace-domain-06-1.md).

## Boundary and input

`src/workspace-local/` accepts an already-valid `WorkspaceHandleV2`, an explicit canonical absolute Linux execution root **equal to the handle's execution-root locator**, and a trusted `observeSource` callback. The callback must actually re-observe the registered source/root association; returning the old source object without inspecting the source is not a freshness check. Source is checked before and after capture against the validated, detached handle observation (semantic subject and ID; audit time excluded). A local control root is validated as well and checked for replacement. For separate local roots, physical identity/lexical nesting/symlink aliases cannot make the execution tree coincide with the control tree. A root locator is not a minted workspace identity or ownership claim. No root discovery, cwd lookup, parent search or user-home scanning occurs. Source association digest is not reverse-engineered from the root path. Registration and identity authentication remain external.

The adapter imports only read-only filesystem operations. It does not create, modify, chmod, remove, lock, initialize `.aira` or `.git`, prepare a worktree/copy/snapshot, persist anything, touch mtimes, or invoke Git or a worker. Filesystem reads may cause incidental **atime** changes according to the host mount; this is not an explicit touch operation. Trusted callbacks and test-only hooks are caller code, not adapter I/O and must themselves preserve their respective contracts.

## Pinned inspection policy

`aira.dev/workspace-local-inspection/v1` is a frozen version-tagged canonical-JSON/SHA-256 policy subject. Its hash pins iterative traversal, exact UTF-8 logical paths, no-follow and same-device checks, 64 KiB streamed SHA-256, POSIX executable bits, raw symlink target bytes, policy-visible empty directories, exact subtree exclusions and all bounds. Policy changes require a new identity; the caller cannot silently override the limits. This implementation is certified only for trusted local Linux roots with `O_NOFOLLOW`, `O_DIRECTORY`, `O_NONBLOCK`, and a local filesystem (known network/FUSE filesystem types are rejected). It is not a portability claim for Windows, macOS, or remote/mutable distributed mounts. The default policy's maximums are:

| Bound | Limit |
| --- | ---: |
| logical depth below execution root | 64 |
| entries enumerated in one directory | 50,000 |
| entries visited across all directories | 250,000 |
| path, UTF-8 bytes and UTF-16 characters | 4,096 each |
| manifest entries | 250,000 |
| aggregate regular-file bytes hashed | 16 GiB |
| symlink target bytes | 16 KiB |

A single regular file may consume the entire aggregate budget; it is streamed, not buffered. Directory enumeration stops before an unbounded list is sorted. Total entries include excluded names encountered at their parent; excluded subtrees are not traversed. An empty execution root yields an empty entry list: the root itself is implicit in the binding and has no representable project-relative path.

## Semantic tree and strict fingerprint

`aira.dev/workspace-local-tree/v1` has sorted entries `{ path, state }`, inspection-policy hash, capture-policy hash, and a canonical-JSON SHA-256 hash over those fields. This is a provider-neutral **worktree observation**, not a Git-classified manifest or retained snapshot. Files have SHA-256 of exact bytes, exact byte count and one executable boolean (`mode & 0o111`); symlinks have SHA-256 and byte length of raw link-target bytes (no target dereference); physically or policy-visible empty directories have a marker. Nonempty directories, owner, group, non-executable permission bits, inode, device, timestamps and traversal order do not enter semantic identity. Device and inode of the execution root appear only in separate operational audit data. Hardlinked included files and special files (FIFO, socket, device) fail closed. Mount crossings are rejected.

Logical paths use the existing `exactPathSchema`, with the 06-1 4,096-character limit and an additional UTF-8 byte bound. Invalid traversal, absolute names, backslashes, colons, controls, glob tokens, duplicate normalized/casefold aliases and non-roundtrippable paths fail closed, not normalized into a new identity. On Bun, directory names are decoded by `opendir(utf8)`; an undecodable POSIX name cannot be reopened under its decoded path and therefore fails the scan. Two names decoding to the same logical spelling also fail. Entries use the same `compareText` JavaScript string ordering as the 06-1 manifest constructor. Symlink targets are **bytes**, not logical paths: external, dangling and internal links are recorded without following. Whether a worker may dereference one is a later enforcement question. Only executable state is semantic for regular files; Unix permission changes that do not change this bit do not alter a fingerprint.

The pinned `aira.dev/workspace-capture/all-project-content/v1` policy excludes the **entire top-level `.aira/**`** (both `.aira/state/**` and Steering/authoring/materialized surfaces) in both roles. This is deliberate, not a mistaken narrower state-only exclusion. Exact Steering, Spec and Context control inputs need independent pins and host control; workspace content does not grant them authority. The entire top-level `.git` path is excluded whether directory, linked-worktree indirection file, or symlink; Git semantic metadata is not parsed here. A nested `.git` in included scope is rejected as a possible nested repository. Additional exclusions are only the sorted explicit provider-cache paths/reasons/affected consumers already pinned in the v2 capture-policy hash; they use exact subtree boundaries. `.gitignore`, generated/ignored ordinary files, and caches without an explicit pinned exclusion remain included. Exclusion aliases fail closed rather than broadening the exclusion. Policy-visible empty directories are included when all children were excluded.

`WorkspaceLocalInspection.status` indicates **filesystem scan completeness**. `fingerprint_status` independently indicates `constructed` or `incomplete`; a complete local scan with missing Git/classification/retention evidence returns a tree and a `workspace-inspection-fingerprint-incomplete` diagnostic, but never a partial fingerprint. A failed scan has no tree hash or fingerprint. All returned data, including diagnostics and audit fields, is detached/frozen; failed paths and exclusion summaries are sorted. Operational diagnostics are not folded into the semantic tree hash. `compareLocalInspections` compares complete local trees and reports additions/removals, content, symlink and executable changes, root replacement and inspection/capture policy drift; it does not use mtime for semantic equality.

The exact existing `WorkspaceFingerprintV2` is constructed **through** `createWorkspaceFingerprint`; no adapter-specific fingerprint version exists. Snapshot-backed sources require a retained `BaseRevision` in the valid handle, `dirty_state: clean` and `overlay: none`, a trusted `verifyRetainedBase` callback that verifies retained manifest **and bytes** before and after construction, and an explicit exhaustive per-path category list from the caller. The adapter cannot infer tracked, untracked or ignored from a path. The callback's result must equal the retained base in the handle; this stage does not itself provide a snapshot store or certify that callback. A clean same-root snapshot additionally requires the reviewed `observed_tree` digest to equal this adapter's local-tree digest, so its source observer must use the same versioned digest algorithm. For a separate execution root, edits since its source base may be represented; the source callback must separately prove source freshness. Dirty snapshot overlay reproduction and base-only overlay/materialization proof are deferred and return an incomplete fingerprint here. An arbitrary mutable non-Git tree with `base: unmaterialized` cannot form a valid handle or complete fingerprint.

Git sources return a complete local **filesystem component** when safely captured but **always** return an incomplete final fingerprint in 06-2A. Git stage-0 index states, tombstones, tracked/ignored/untracked classification, repository index/tree components, submodule semantics and base-commit verification cannot be inferred from the walk. 06-2B must supply and validate these independently before a Git fingerprint can be claimed complete. No Git commands, index parsing, repository discovery or status guessing occur in this adapter.

## Race and security model

The guarantee is **best-effort race-detected coherent observation**, not an atomic snapshot or a proven stable verification interval. The root and local control role are checked before/after, ancestors are checked against symlink/device substitution, opened regular files use `O_RDONLY|O_NOFOLLOW|O_NONBLOCK` and pre/open/post device, inode, type, link count, size, mode, nanosecond mtime/ctime and read byte-count checks. Symlink targets are read without following and rechecked by lstat; directories are opened no-follow, incrementally enumerated, checked before/after listing and rechecked at the end. Previously captured files/links are rechecked at the end, including after trusted retention callbacks. Detected change or an unsafe entry aborts the semantic result. Runtime probes and returned audit inode/device observations are **diagnostic only**.

Node/Bun pathname APIs are not `openat2`/dirfd-confined traversal. `opendir(path)` and `readlink(path)` have a narrow pathname race despite surrounding checks; a hostile same-permission process able to swap ancestors during reads can escape these best-effort checks. Repeated content changes that restore all observable metadata (or writes after the last check), transient writes between checks, bind mounts on the same device, and a lying caller's source/retention callbacks are not ruled out. A matching digest or two scans does **not** prove uninterrupted stability. Trusted host ownership/quiescence, kernel-level path resolution and an enforcing backend/runner are needed before asserting verification-grade stable input consumption. A scan is observation, not lifecycle authority or a capability grant.

Stable issue codes include `workspace-inspection-root-invalid`, `root-unsafe`, `root-changed`, `entry-unsafe`, `entry-changed`, `nonregular`, `depth-limit`, `entry-limit`, `byte-budget`, `path-invalid`, `policy-incompatible`, `incomplete` and `fingerprint-incomplete` (all prefixed `workspace-inspection-`).

## Reuse and deferrals

Reused 06-1 strict v2 handle/source/policy/manifest/fingerprint constructors, `exactPathSchema`, `compareText`, shared canonical JSON and `hashBytes` for links; streamed regular-file SHA-256 uses Node's incremental implementation with the same `sha256:<hex>` format, verified against `hashBytes`. Steering native-source and AGENTS discovery supplied the root/ancestor/no-follow/open-stat/late-recheck patterns. Storage path checks are write-oriented and use mutable storage layout, so they were not imported into this read-only adapter. No low-level framework was extracted and no pure domain file changed.

06-2B2 reuses the same no-follow walker through a tree-only bootstrap API, plus a metadata-only post-Git freshness recheck. Neither API creates a fingerprint alone; the original handle-bound source checks remain unchanged. See [06-2B2 capture](workspace-capture-06-2b2.md). 06-2B owns Git base/index/overlay classification. 06-3 owns WorkspaceStore and lifecycle authority. 06-4 owns retained snapshot creation, provider preparation, source handoff and disposal. 06-5 owns adversarial audit and cross-domain gate. Context resolver, capability enforcement, verification runner, scheduling and worker/CLI/Pi integration remain untouched.
